# SU-ERP Mobile App — Design

**Date:** 2026-08-02
**Status:** Approved for planning
**Scope:** React Native (Expo) app for students, wardens, drivers, and canteen owners,
plus the backend work required to support it.

---

## 1. Goal and scope

Ship one React Native app covering four roles — **student, warden, driver,
canteen-owner** — that reaches feature parity with those roles' web dashboards and
adds capabilities the web app cannot have because it lacks device hardware.

Admin and superadmin stay web-only. Logging in with those roles shows a "use the web
portal" screen; the app never renders a partial admin dashboard.

### Non-goals

- No admin/superadmin surfaces.
- No BFF/aggregation service. The app calls the existing Nginx gateway directly.
- No full local-first two-way sync. Server always wins.
- No new ML models. Every ML touchpoint reuses the existing `ai-service`.
- No voice/speech-to-text grievance intake.

---

## 2. Architecture

### 2.1 Stack

| Concern | Choice | Reason |
| --- | --- | --- |
| Runtime | Expo (managed) with **dev-build** | BLE, geofencing, biometrics, and widgets are unavailable in Expo Go |
| Language | TypeScript | matches the web app |
| Routing | Expo Router (file-based) | mirrors the Next.js App Router structure already in the repo |
| Server state | TanStack Query + MMKV persister | read cache and offline hydration in one layer |
| Client state | Zustand | session, device identity, connectivity |
| Styling | NativeWind | Tailwind syntax shared with `frontend/su-erp-web` |
| Local DB | `expo-sqlite` | offline mutation queue |
| Secrets | `expo-secure-store` | Keychain / Keystore for the refresh token |
| Push | Expo Push Service | no APNs certificate or FCM project setup required |
| Crash reporting | Sentry | tagged with `tenant_id` and `request_id` |

### 2.2 Repository layout

```
mobile/su-erp-app/            # new — sibling to frontend/su-erp-web
  app/                        # Expo Router routes
    (auth)/login
    (student)/...
    (warden)/...
    (driver)/...
    (canteen-owner)/...
  src/
    lib/api/                  # one module per backend service, pure functions, no React
    lib/offline/              # mutation queue, replay, idempotency keys
    lib/device/               # camera, GPS, BLE, biometrics, QR — behind interfaces
    features/<domain>/        # screens + hooks
shared/api-types/             # new — request/response types shared by web and app
```

### 2.3 Layer boundaries

Four layers, each independently understandable and testable:

- **`lib/api/*`** — HTTP only. Takes typed input, returns typed output. No React, no
  hardware, no storage. Depends on the shared `apiClient`.
- **`lib/offline/*`** — owns the SQLite queue and replay loop. Depends on `lib/api`.
  Knows nothing about screens.
- **`lib/device/*`** — every hardware capability behind a narrow interface
  (`Camera`, `Location`, `Ble`, `Biometrics`, `QrScanner`). Tests substitute fakes; CI
  never needs a physical device.
- **`features/<domain>/*`** — screens and hooks. Imports the three layers above. Never
  calls a native module directly.

A screen file that grows past roughly 200 lines is a signal to extract a hook or a
child component.

### 2.4 Network path

```
App ──► Nginx gateway :8080 ──► services (/api/v1/*)
```

Identical to the web app: same JWT (HS256), same tenant claim, same routes. No new
routing layer.

A single `apiClient` wrapper owns:

- base URL resolution per environment
- bearer token injection
- `X-Request-Id` generation
- `Idempotency-Key` header for queued mutations
- 401 → refresh-and-retry-once
- connectivity detection and handoff to the offline queue

### 2.5 Role routing

Role is read from the JWT claim at login and selects which route-group shell mounts.
One binary, four shells. Role changes take effect on the next token refresh.

## 3. Auth hardening (backend — blocks app work)

The current `auth-service` cannot safely serve a mobile client: it has no refresh-token
rotation, no logout, and no device concept. Four additions.

### 3.1 Refresh-token rotation and blacklist

New tenant-scoped `RefreshToken` model:

| Field | Notes |
| --- | --- |
| `jti` | token identifier |
| `user_id` | owner |
| `device_id` | binds the chain to one device |
| `expires_at` | 30 days |
| `revoked_at` | null while live |
| `replaced_by` | forms the rotation chain |

Rules:

- Every `POST /refresh` issues a new refresh token and revokes the presented one.
- Presenting an already-revoked token is **reuse detection**: revoke the entire chain
  for that device and force re-login.
- `POST /logout` revokes the presenting device's chain.

### 3.2 Device sessions

New tenant-scoped `Device` model: `device_id` (UUID generated by the app, persisted in
SecureStore), `platform`, `model`, `push_token`, `last_seen_at`, `is_stale`.

Login binds a refresh chain to a device. Users can list active devices and revoke any
one of them. This same table is the push-token registry — one table serves both
concerns.

### 3.3 Biometric gate

Biometric data never leaves the device and is never sent to the server. FaceID or
fingerprint unlocks the refresh token held in SecureStore; server-side the exchange is
an ordinary refresh.

Payments require a **fresh** biometric assertion (within 60 seconds) before the request
is sent. This is a client-side control; the server-side protection against a bypassed
client remains the existing idempotency key on `/pay`, so no bypass can double-charge.

### 3.4 Token lifetimes and storage

| Token | Lifetime | Storage |
| --- | --- | --- |
| Access | 15 minutes | memory only — never written to disk |
| Refresh | 30 days, rotating | `expo-secure-store`, biometric-gated |

MMKV and the SQLite queue hold cached **data** only. No credential is ever written to
them.

### 3.5 Tests

pytest in `auth-service`, following the existing tenant-isolation test style: rotation
happy path, reuse detection revokes the chain, cross-tenant refresh rejected, revoked
device rejected, logout revokes only the calling device.

## 4. Offline layer

### 4.1 Read cache

TanStack Query persisted to MMKV. Each query declares its own `staleTime` and TTL. When
offline, the cache serves immediately and a banner shows the data's age
("Offline — showing data from 14:32").

Cached read surfaces: timetable, canteen menu, my allocation, my invoices, notification
inbox, my passes, driver's assigned route, warden's block roster.

### 4.2 Write queue

Only these mutations queue. Every other mutation fails fast with an explicit offline
error.

| Mutation | Actor | Why offline is real |
| --- | --- | --- |
| Mark attendance session | student | classroom dead zones |
| Update order status | canteen-owner | kitchen basements |
| Scan / verify pass | driver, warden | moving bus, gate |
| Create grievance (with media) | student | hostel blocks |
| Visitor log entry | warden | gate |
| GPS breadcrumb batch | driver | tunnels, route gaps |

**Payments never queue.** Fee payment and canteen checkout are online-only and raise a
hard error when offline.

### 4.3 Queue mechanics

SQLite table with columns `id`, `endpoint`, `method`, `body`, `attempts`, `created_at`,
`status`.

- `id` is a UUID generated at capture time and sent as the `Idempotency-Key` header.
  Backend endpoints reuse the existing idempotent-inbox dedupe pattern, so a double
  replay is a no-op.
- Replay is sequential on connectivity regain, with exponential backoff.
- After 5 failed attempts a row moves to a "Failed to sync" screen where the user
  retries or discards it.

### 4.4 Conflict rule

**Server wins, always.** A queued mutation rejected with 409 or 422 (for example, an
order already advanced by another operator) is dropped from the queue and reported to
the user. It is never retried and never merged. This is the reason full local-first sync
was rejected.

### 4.5 Media queue

Grievance photos and videos are written to the app filesystem and uploaded when
connectivity returns. The local file is deleted only after the server returns 201.

### 4.6 Tests

Jest against a mocked client — no device required: replay ordering, dedupe on double
replay, backoff schedule, 409-drop path, media upload then local delete.

## 5. Core parity features

### 5.1 Student

- **Home** — next class, today's bus, pending dues, unread notifications; single
  cached screen
- **Hostel** — my allocation, request allocation (starts the existing saga), leave
  request, complaints
- **Fees** — invoice list, invoice detail, pay (online-only, biometric-gated)
- **Canteen** — menu, cart, checkout, live order status
- **Transport** — my pass, route and schedule, book seat
- **Grievance** — raise, track, comment thread
- **Notifications** — inbox, mark-read, deep-link into the source screen
- **Profile** — active devices, revoke device, logout

### 5.2 Warden

- Block roster and room-occupancy grid
- Allocation approvals and releases
- Leave-request approve / reject
- Grievance queue sorted escalated-first (consumes the existing ML escalation), status
  change, resolve
- Visitor log entry

### 5.3 Driver

- Today's trip: assigned route, stop sequence, student manifest
- Start / end trip (drives GPS broadcast, §6.3)
- Scan boarding pass (§6.1)
- Trip history

### 5.4 Canteen owner

- Live order board with placed / preparing / ready / completed lanes
- Status advance, guarded by the existing legal-transition rules
- Menu management: price edit, availability toggle
- Scan pickup token (§6.6)
- Daily sales summary

### 5.5 Backend endpoints this requires

Small additions to existing services:

- `hostel-service` — `VisitorLog` model and endpoints (designed but never built)
- `transport-service` — driver trip start/end, manifest, breadcrumb ingest
- `grievance-service` — `PATCH /status` (listed as missing in `REMAINING_MODULES.md`)

Everything else already has working endpoints.

## 6. Mobile-only features

Each feature below is impossible on the web app because it requires device hardware.

### 6.1 QR e-pass and scanner

The server signs a pass payload with HS256 using the existing key infrastructure:

```
{ tenant_id, pass_id, user_id, valid_from, valid_to, nonce }
```

The holder's app renders it as a QR that re-renders every 30 seconds from a
TOTP-style rolling nonce, so a screenshot expires within 30 seconds.

The driver/warden scanner verifies the signature **offline** — the verification secret
is cached at app login — checks the validity window and nonce drift, and records the
scan through the offline write queue.

New backend: pass-signing endpoint in `transport-service`, `ScanLog` model. Closes the
"QR e-pass generation" gap.

### 6.2 Geofenced attendance

Faculty opens a session **from the web dashboard** (faculty is not an app role); the
server returns `{ session_id, geofence: { lat, lng, radius_m }, rolling_code }`. The
app-side actor is the student marking attendance.

A student may mark attendance only when **both** hold:

1. the device is inside the geofence, and
2. the submitted rolling code is current (rotates every 15 seconds; displayed on the
   faculty's web dashboard).

Anti-proxy layers: geofence, rolling code, one-device-per-student binding (§3.2), and a
mock-location detection flag recorded with the mark.

BLE proximity is an optional stricter mode, deferred past v1: it requires a beacon in
the room (a dedicated BLE tag, since faculty has no app), which the student's device
must observe, making GPS spoofing alone insufficient. v1 ships geofence plus rolling
code only.

This fills the entire `attendance-service` stub — session, mark, summary, defaulter
computation.

### 6.3 Live bus tracking

The driver app posts a GPS breadcrumb batch every 15 seconds while a trip is active
(queued offline, flushed on reconnect). `transport-service` writes the last known
position to Redis in a tenant-namespaced key with a 60-second TTL, reusing the existing
seat-cache pattern. Students read position and ETA.

ETA is computed from remaining stop distance at a rolling average speed — no ML model
and no external maps API. A push fires when the student's stop enters the arrival
window ("bus arriving in 5 min").

Closes the "driver live-trip dashboard" gap.

### 6.4 Biometric lock and payment unlock

App-launch biometric gate, plus a fresh biometric assertion before fee payment and
canteen checkout. Detailed in §3.3.

### 6.5 Camera-first grievance with auto-purging media

The student photographs or records the issue. The app attaches GPS and infers block and
room from the nearest known geofence, then uploads.

**Retention:** media is stored with `expires_at = resolved_at + 7 days`. The existing
celery-beat schedule (the same beat that drains the outbox) sweeps and deletes expired
blobs. The ticket row retains only metadata: `media_count`, `sha256[]`, `captured_at`,
`purged_at`.

Both the student's log and the warden's log then show
"3 attachments, purged 2026-08-09" — the evidence is gone, the audit trail is intact. A
ticket reopened inside the 7-day window still has its media.

### 6.6 Canteen pickup token

When an order is ready the student's phone displays a signed token QR using the same
scheme as §6.1. The canteen owner scans it to mark the order completed. Scanning is the
only path to `completed` from the app, so the transition provably corresponds to a real
handoff.

### 6.7 Widgets and Live Activity

Home-screen widget showing next class, bus ETA, and order status. On iOS, a lock-screen
Live Activity runs while a canteen order or bus trip is in flight. Data comes from a
shared app-group store refreshed by push — no additional API surface.

### 6.8 Offline document vault

Receipts, hall tickets, and the student ID card are downloaded to the app filesystem and
readable with no network. Files are encrypted at rest with a key held in SecureStore and
exported through the native share sheet.

## 7. Push notifications

Device tokens register into the `Device` table (§3.2) at login.

A new `push-channel` consumer in `notification-service` subscribes to the events it
already consumes — `payment.success`, `allocation.confirmed`, `grievance.scored` — plus
new ones: `order.ready`, `bus.approaching`, `pass.issued`.

The channel sits behind an interface: `ExpoPushChannel` today, `FcmPushChannel` later,
with no consumer rewrite. Delivery failure on an expired token marks the device stale.

Every push carries a deep-link path so tapping it opens the exact screen. The in-app
inbox remains the source of truth; push is a nudge, never the only copy of a message.

## 8. Error handling

| Condition | Behavior |
| --- | --- |
| No network | cached data plus offline banner; mutations queue or fail fast per §4.2 |
| 401 | silent refresh and retry once; a second 401 logs out to the login screen |
| 403 | "not permitted for your role" — no partial render |
| 5xx | retry with backoff, then an error screen showing `X-Request-Id` for log tracing |
| Hardware permission denied | feature-specific explainer plus a settings deep-link; the rest of the app stays usable |
| Crash | reported to Sentry, tagged with `tenant_id` and `request_id`, PII scrubbed |

## 9. Testing

| Level | Tool | Coverage |
| --- | --- | --- |
| Unit | Jest | API modules, offline queue, QR sign/verify, ETA math, role routing |
| Component | React Native Testing Library | screens with mocked hooks, mirroring the existing 19 frontend tests |
| Hardware | fakes at the `lib/device/*` interfaces | CI never needs a physical device |
| Backend | pytest per service | auth rotation, attendance sessions, scan logs, visitor log, media purge sweep |
| E2E | Maestro | login → pay → order → scan happy paths; run manually, not in CI |

CI gains one `mobile-lint-test` job in the existing GitHub Actions workflow. EAS builds
stay out of CI — too slow and too costly for every push.

## 10. Build and distribution

- **Development:** EAS dev-build. Expo Go cannot host BLE, geofencing, or widgets.
- **Demo:** EAS preview channel producing an internal Android APK.
- **iOS:** TestFlight only if an Apple developer account is available; otherwise the
  demo is Android-only, which is sufficient for the capstone.

### Local resource constraint

An i5-12500H cannot run all 14 services alongside a React Native bundler. Mobile
development uses the `default` compose profile — the eight fully built services the app
actually needs (auth, hostel, finance, notification, transport, canteen, grievance, ai)
plus infrastructure. The observability profile stays opt-in.
